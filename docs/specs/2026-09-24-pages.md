# Chapters have pages

*2026-09-24. Issue #78. Brainstormed with the user the same day; every rule a
player can see is theirs, quoted or approved line by line.*

## 1. Why

#78 asked for "the next step declares its conditions": at Port Cinder a player
can fight the harbor pirates, and so leave port, before the ship is fitted out.
The first reading was a `requires` field on rows. The user reframed it:

> this is more a reference that we should modify the books a bit if we want
> to have things gated. My thinking is that chapters can have pages.

So no row grows a condition. **A gate is written into the book as a page
boundary.** Later in the brainstorm the user added how a press behaves when
something is missing (sections 4.2 and 4.3): the game queues what is missing,
deepest first, rather than refusing. That changes every press, not only a
closing row's, and is part of this slice.

### 1.1 A correction

The 2026-09-22 spec (`2026-09-22-books-chapters-verbs.md` section 2) says "the
big event is always a fight". That was never the user's rule: "We could have a
book that is all about picking daisies, there is no fighting." **A chapter ends
on its last page's closing row, whatever that row is.** That line in the 09-22
spec, and #38's summary of it, are corrected by this slice.

## 2. The rules (the user's)

1. **A chapter is a sequence of pages.** Only the current page's rows are on
   screen and in play.
2. **A page ends on a closing row** (brainstorm pick B). It is an ordinary
   one-time row: queued, played and automated like any other. It **cannot
   start until every other one-time row on its page is done**; a player's
   order for it queues those rows first (section 4.2).
   Completing it turns the page.
3. **Pages replace, and authors carry rows across** (pick B+C). Each page lists
   its own rows. The same row may be listed on several pages of its chapter,
   and its kept progress goes with it (progress already lives on the row).
4. **Carrying is a guideline, not a rule.** "There are not set rules for this,
   but there should be guidelines." The validator does not enforce them; they
   are written for authors (section 6).
5. **A chapter ends on its last page's closing row.** Completing it casts off
   to the next chapter's first page, or, in the last chapter, finishes the
   book.

## 3. Decided in the brainstorm (not asked; nothing a player sees changes from today's behaviour)

- **Death restarts at chapter I, page 1**, as it restarts at chapter I today.
- **A page turn drops queued orders for rows the new page does not list,** as
  a cast-off drops orders the next port does not have. The chips stay set. Nothing
  else is dumped: items stay (a cast-off still dumps non-food, as today).
- **No going back a page.**

## 4. The shape (implementation's call)

```ts
export interface Page {
  /** Shown after the chapter's name: "I · Port Cinder · Fitting out". */
  readonly name: string;
  /** Rows in display order. */
  readonly order: readonly ActionId[];
  /** The closing row: a one-time row in `order`, its last one-time row. */
  readonly closes: ActionId;
}

export interface Chapter {
  readonly head: ChapterHead;
  readonly pages: readonly Page[];   // replaces `order` and `event`
}
```

- **The page is derived, not stored** (Revision 1, from the panel): the
  current page is the first page of the current chapter whose `closes` is not
  in `completedOneTime`. Closers are one-time and each is on exactly one page,
  so this is always right. No `GameState` field, nothing to reset on a
  cast-off or rebirth, nothing new in the save, and a save from before pages
  lands on the right page by itself.
- **`pageOf(state, content)`** in `src/engine/rows.ts` returns the current
  page, and `here()` means "on the current page". Readers of today's `.event`
  split two ways: the **page rule**, `delayFor` in `fight.ts` and the play
  policy read the page's `closes`; **departure** (resolve's `departing`
  provisioning, `castOff`, the "casts off" tag) reads `eventOf(chapter)`, the
  last page's `closes`.
- **The chapter's event is its last page's `closes`.** `Book.finish` stays, and
  the validator checks it is the last chapter's last page's `closes`.
- **The closing block is a new `StartBlock` kind**: `{ kind: 'page', waits:
  ActionId[] }`, the page's one-time rows still undone. Resolve checks it on
  the top entry explicitly, after `isDone` and before the fight check and
  provisioning (it never consulted `blockOf` there). What an order for a
  blocked closer does is section 4.2.
- **A page turn drops orders, never automation.** Automation is kept across
  lives and only acts on rows here, so a chip on Salvage survives page 2 and
  is live again next life.
- **JIT only where it can act.** A row is offered JIT only if some row on a
  page it shares spends its output. The wardens make the inner door, which is
  spent on the next page, so the wardens get no JIT chip (the panel reproduced
  a freeze at exactly that chip).
- **A page turn is an event**, `{ type: 'pageTurn', chapter, page }`, narrated
  in the log with the new page's name. The closing row's own beat prints as
  every one-time beat does.
- **The save** gains nothing but the `pageTurn` line in its log check. The
  book's `version` goes to 2 for the record; the load does not read it.

### 4.1 Validator

Replacing the chapter rules in `src/data/validate.ts`:

- every chapter has at least one page, and every page at least one row;
- a page's `closes` is a one-time row in its `order`, and its last one-time row;
- **a one-time row is listed on exactly one page;** a repeatable row may be
  listed on several pages, all in one chapter;
- every row is on some page;
- the first page of the first chapter has a row that costs and needs nothing
  (today's "opens" rule, moved to the page);
- `finish` is the last chapter's last page's `closes`;
- **every item a page's rows cost is made on that page by a row other than
  its closer; every item they need (held, not spent) is made on that page by a
  row other than its closer, or by a one-time on an earlier page of the chapter
  (only a one-time's product is sure to be held);** a
  one-time row never costs or needs what only a one-time listed after it on
  its page makes; no row is listed twice on one page; and no row
  needs more of an item than the base stack cap holds. Food has no
  exception: it is eaten every tick, so a stock from an earlier page cannot be
  relied on. A key survives a page turn but not a
  cast-off, and a harvest dropped from a page cannot restock it, so an
  unfinishable page is caught here, not by a 60-day headless play.

### 4.2 Prerequisites are shown, honoured, and added (the user's call)

> If those are displayed, and we have pre-reqs, then they should be honored.
> if they need to be added, the should be added. It makes sense that
> re-outfitting a ship has some sort of order.

- **Shown.** While any of its page's one-time rows are undone, a closing row
  says so at rest, without a press: "after: the hull, a net, a satchel".
- **Honoured and added.** Whoever queued it (▶, `+`, Shift), a closer at the
  top of the queue whose page is not done pulls its prerequisites **one at a
  time, the first undone in page order**:
  - queued below the closer already: that entry moves to the top, keeping its
    `id`, who queued it and any `for` it already had, and gaining none, and the
    entries that serve it (its supply orders, a harvest delay) move with it in
    their order (so removing the closer never removes the player's own order,
    and no row ever has two supplies). An order of automation's own that moves
    up is tied to the closer instead, so it joins the closer's chain and a
    player's closer supplies it whatever the chips (code panel);
  - otherwise: it is queued at the top `for` the closer's entry, so it leaves
    with the closer through `withoutOrphans`, and there is only ever one entry
    `for` the closer (the property test's supply invariant holds);
  - when it completes, the closer is back on top and pulls the next.
- **Nothing waits forever at the top.** A prerequisite pulled in this resolve
  and gone again (for any reason: short at any gap, a fight backing off, full)
  is not pulled a second time in that resolve; the closer then leaves with a
  `popped` line, reason `page`, naming what it waits on. This is new selection
  logic in resolve, not a call into the supply chain (`supplyVia` finds makers
  of items, and a closer like the sails costs none); it reuses `for`,
  `withoutOrphans`, `enqueue`'s call shape, and a per-resolve `tried` set.
- **The fight check waits for the start.** A ▶ on a closer that is a fight
  (the wardens, the guardian) is not refused as "would stop" while its page
  is unfinished; `playBlock` skips the hurt check under a page block, and
  resolve checks the fight when the closer would actually start. Shift forces
  the closer, not its prerequisites.
- **Automation orders a waiting closer only when its next prerequisite can
  start**, and the pull then succeeds. A JIT one-time acts only on demand, and
  the closer's order is that demand: without this, a compass on a priority
  with the wardens and the halls on JIT froze the game (found at task 2a by
  the prioritized headless player). Ordering a closer whose pull would fail
  is what re-ordered it every tick without time passing, so that stays out.
- **The page after the finish** is the last chapter's last page, so the screen
  behind the finish card has a page.

### 4.3 A press queues its whole chain (the user's call, Revision 5)

> if the thing can be harvested, it should be harvested. If I click play on A,
> that needs B, that needs C, and B and C are not off, then C -> B are queued,
> with A at the bottom. if B also needs D, D goes on top. the goal is to be
> very clear to the player what is going on, but to also help

- **A player's order pulls its chain, whoever's chips are off.** When a
  player's order (▶, `+`, Shift), or any entry that serves one down a chain of
  `for`, is at the top and cannot work, what it lacks is queued in front of it,
  deepest first: a closer's undone page rows (section
  4.2), and for any row short of an item, a row on the page that makes it,
  chip earned or not. The pulled rows are themselves pulled for, so the chain
  goes as deep as it needs: `Salvage > Rig the hull > Salvage > Tinker a net >
  ... > Rig the sails`.
- **A chain supply is a plain supply order** `for` the entry, with no `left`
  count (the `for` look-ahead already stops it at what the entry owes, capped
  by the stack), and it is queued directly: it does not wait behind
  automation's higher-ranked producers. So the chain in the queue is only the
  order and what it needs.
- **This is every press, not only closers.** ▶ on Rig the hull with no scrap
  queues Salvage in front of it, where today it refuses ("missing 16 scrap ·
  Salvage some!").
- **"Not off" is read as "can run".** On life 1 every chip is off and the user
  wants the help, so a chip's mode does not gate the pull; a row that cannot
  run at all (nothing on the page makes what it needs) ends the chain, and the
  chain leaves with a log line naming what is missing (section 4.2's guard).
- **Automation's own orders are unchanged:** an order automation placed, and
  its supplies, still go through chips, as today (#72: automation does what the player set).
- **Clear to the player:** the chain is in the queue as it is built, each
  pulled entry tied to the order it serves, so removing the order removes its
  chain (`withoutOrphans`).

## 5. The Windward Run, repaged (approved by the user)

```text
I · PORT CINDER
page 1  Fitting out      Fish · Salvage · Rig the hull · Tinker a net · Tinker a satchel
                         closes on: Rig the sails                       (new row)
page 2  Pirates!         Fish · Fight the harbor pirates
                         closes on: Fight the harbor pirates
page 3  Casting off      Fish · Rig the ship for the open sky
                         closes on: Rig the ship for the open sky       (new row; the chapter's end)

II · THE HOLLOW ISLE
page 1  Landfall         Fish the eel runs · Salvage the ruin · Rig brass fittings
                         · Tinker a sea chest · Tinker a cutlass
                         closes on: Fight the wardens
page 2  The inner halls  Fish the eel runs · Search the halls
                         closes on: Fight the guardian                  (the chapter's end)

III · THE GILDED FORTUNE
page 1  At the tables    Talk to the dealers · Talk to the kitchens · Rig the high dock
                         · Tinker a gilded trunk
                         closes on: Talk past the door
page 2  Upper decks      Talk to the dealers · Talk to the kitchens · Fight the enforcers
                         closes on: Search the salons
page 3  Varro's table    Talk to the dealers · Talk to the kitchens
                         closes on: Talk to Varro                       (the book's finish)
```

- **The closer is part of its page's `order`**, listed last among its one-time
  rows; the table names it separately only for reading.
- **Two new rows**, both `rig`, one-time, no item costs, each with a beat:
  `sails` ("the sails") and `openSky` ("the ship for the open sky"). The
  pirates' beat, which today sails us off, is rewritten for a fight that no
  longer ends the chapter; the leaving beat moves to `openSky`. Words are a
  first draft for the user.
- **The existing `needs` stay.** A page boundary now also orders halls after
  the wardens, and so on; the keys are harmless and keep a row honest if it is
  ever moved.

### 5.1 Numbers (decision #3)

Every number here goes to the user **before it lands on `main`**:

- the two new rows' `expCost` (in `balance.content.windward`);
- **the doubled port I/II upgrade costs.** They were doubled partly so a
  harvest's chip arrives no later than the one-times it feeds (#72, #23). The
  page boundary now closes that lock-out by structure, so they may no longer be
  needed.

Method: the headless play (`src/engine/play.ts`) reads the book's length and
life lengths with the repage at provisional values, then at candidate values.
The readings, not a recommendation alone, go to the user. Implementation lands
provisional values marked `UNDERIVED, provisional (#78)` on the branch; the
branch does not merge until the user has picked.

## 6. Guidelines for authors

For `book-author` (#52) and anyone writing a book by hand:

- **Carry the food.** Early on especially: a page with no food is a page where
  the player dies before they can play it, and it isn't fun.
- **Keep a harvest while something on the page spends its output.** Salvage
  leaves the Hollow Isle after Landfall because nothing after it spends brass;
  the dealers stay through the Gilded Fortune because the kitchens spend chips.
- **A gate is a page boundary.** If something must happen before something
  else, put them on successive pages rather than reaching for a condition.

These go in `docs/authoring.md` (new), linked from the README's book section.

## 8. Tests

- **Validator:** each rule in section 4.1 has a book that breaks it and
  names the problem.
- **Engine:** a closing row at the top pulls its page's undone one-times one at
  a time (section 4.2), leaves with a line when one cannot be done, and starts
  once they are done; completing it turns the page, drops orders for
  rows the new page lacks, keeps those it lists (with their progress), and
  keeps items; the last page's closing row casts off, and in the last chapter
  finishes; a new life is on page 1.
- **The chain (4.3):** ▶ on the hull with no scrap queues Salvage `for` it
  and the hull completes; ▶ on the sails with an empty pack closes the page
  with no further input; a three-level chain pulls all three; a row nothing on
  the page makes leaves with a line; automation's orders still need chips;
  the chain does not queue behind a higher-ranked automated producer.
- **The property test** (`src/engine/property.test.ts`) plays paged books:
  its invariants gain "every queued entry is on the current page".
- **Save:** a save from before pages, with the wardens done, loads on the
  Hollow Isle's second page (the page is derived); a `pageTurn` line is
  accepted and a malformed one reads corrupt.
- **Headless play:** the Windward Run is finishable by every policy, the prioritized one included, and its
  readings are recorded for section 5.1.
